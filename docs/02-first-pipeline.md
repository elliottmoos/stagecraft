# 2. Your first pipeline

In this chapter you set up a pipelines repo, write one action and one pipeline, and render it.
The pipeline you start here, `service-ci`, grows through the rest of the guide.

## The project

A pipelines repo is a plain Python project. Through this guide it will look like this:

```
pipelines-repo/
  pyproject.toml
  actions.py              # your actions
  pipelines/
    service_ci.py         # pipeline files: Pipeline objects at module level
  tests/
    test_actions.py       # tests for your actions
  values/
    staging.yaml          # Helm values for one installation
  chart/                  # written by `stagecraft render`
    Chart.yaml
    values.schema.json
    templates/
```

You write everything except `chart/`, which Stagecraft generates and you commit, so every change
to what's installed shows up in review.

```toml file=pyproject.toml
[project]
name = "pipelines"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = ["stagecraft==0.0.1"]
```

Pin stagecraft exactly. A new release can change what it renders, and you want that change to
show up as a reviewed diff, not a surprise.

## A first action

Actions are Python classes. This one runs a shell script:

```python file=actions.py
from hera.workflows import Container

from stagecraft.context import CompileContext
from stagecraft.spec import Action


class Shell(Action):
    """Runs a shell script in the chart's shell image."""

    script: str

    def compile(self, ctx: CompileContext) -> Container:
        return Container(
            image=ctx.value("images.shell", str),
            command=["sh", "-c"],
            args=[self.script],
        )
```

Three things to notice:

- `script: str` is a **field**. Actions are Pydantic models, so fields are typed and validated.
- `compile` returns a Hera `Container`: the container this action runs as.
- The image comes from `ctx.value("images.shell", str)`, a **Helm value**, not a literal. Which
  image to use differs per installation, so it belongs to the chart. Chapter 4 explains values in
  depth.

## A first pipeline

```python file=pipelines/service_ci.py
from stagecraft.spec import Pipeline, Stage, Step

from actions import Shell

pipeline = Pipeline(
    name="service-ci",
    stages=[
        Stage(
            "verify",
            [
                Step("lint", Shell(script="echo linting")),
                Step("unit-tests", Shell(script="echo testing")),
            ],
        ),
    ],
)
```

One stage, two steps that run in parallel. A `Step` gives an action a name in its stage. A bare
action works too, and is named after its class (`Shell(...)` alone would be the step `shell`),
but these two both use `Shell`, so each needs its own name. Stagecraft finds the pipeline because
it's a `Pipeline` object at module level; the variable name doesn't matter.

## Values for an installation

The action asked for `images.shell`. Which image to use is decided per installation, so each
environment supplies it in a values file, which Helm reads at install time:

```yaml file=values/staging.yaml
images:
  shell: alpine:3.22
```

Stagecraft never reads this file; it's for Helm. One file per environment
(`values/staging.yaml`, `values/production.yaml`, ...) is a common layout.

## Check, render, look

From the repo root (pipeline files import `actions` relative to the working directory):

```sh
uv run stagecraft check pipelines
# ok: service-ci

uv run stagecraft render pipelines --out chart
# wrote chart/Chart.yaml
# wrote chart/values.schema.json
# wrote chart/templates/service-ci.yaml
```

`check` compiles without writing. `render` writes a complete Helm chart, and writes nothing if
any pipeline fails:

- **`Chart.yaml`** names the chart (`pipelines`; change it with `--chart-name`).
- **`values.schema.json`** requires every Helm value the pipelines use. Here that's
  `images.shell`, a string (shown compacted):

  ```json
  {
    "$schema": "https://json-schema.org/draft/2020-12/schema",
    "type": "object",
    "required": ["images"],
    "properties": {
      "global": {"type": "object"},
      "images": {"type": "object", "required": ["shell"], "properties": {"shell": {"type": "string"}}}
    }
  }
  ```

- **`templates/service-ci.yaml`** is the pipeline as an Argo `WorkflowTemplate`, abridged here:

```yaml
# Generated by stagecraft. Do not edit: change the pipeline and re-render.
apiVersion: argoproj.io/v1alpha1
kind: WorkflowTemplate
metadata:
  name: service-ci
spec:
  entrypoint: main
  templates:
  - dag:
      tasks:
      - name: verify
        template: verify
    name: main
  - dag:
      tasks:
      - name: lint
        template: verify-lint
      - name: unit-tests
        template: verify-unit-tests
    name: verify
  - container:
      args:
      - echo linting
      command:
      - sh
      - -c
      image: {{ .Values.images.shell | quote }}
    name: verify-lint
  # ... verify-unit-tests is the same with "echo testing"
```

Each stage is a small DAG of its steps, and the `main` DAG runs the stages in order. The image
is a Helm expression, `{{ .Values.images.shell | quote }}`: Helm fills it in at install time.
Don't edit the chart; change the pipeline and render again. Re-rendering replaces
`Chart.yaml`, `values.schema.json`, and `templates/`, and leaves anything else in the directory
alone.

To see the shape of a pipeline without reading YAML:

```sh
uv run stagecraft graph pipelines
```

prints a [Mermaid](https://mermaid.js.org) diagram, which GitHub renders in Markdown.

## Run it

Install the chart with an environment's values and submit a run (the namespace and release name
are up to you):

```sh
helm install pipelines chart -f values/staging.yaml -n argo
argo submit --from workflowtemplate/service-ci -n argo --watch
```

Or open the Argo UI, find `service-ci` under Workflow Templates, and submit it there.

## Recap

- An action is a Python class with fields and a `compile` method returning a container.
- A pipeline is configuration: stages of steps, each placing an action under a name.
- Helm values (like the image) are supplied per installation; the generated schema requires
  every one the pipelines use.
- `check` compiles, `render` writes the chart, `graph` draws.
